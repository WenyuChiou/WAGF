### 2. Can any mock fixture trigger a governance intervention

`grep -rn "mock" examples/single_agent/run_flood.py broker/ --include=*.py -l`
surfaces one mock RESPONSE generator actually wired to
`run_flood.py --model mock`: `mock_invoke`, defined at
`broker/utils/llm_utils.py:385` inside the `if model.lower().startswith("mock")`
branch (line 383). It always returns bare `{"decision": <first numbered
option found in the prompt by regex>}` and nothing else -- no
`threat_appraisal`, `coping_appraisal`, or any other PMT construct field,
regardless of agent persona or prompt content.

`broker/validators/agent/agent_validator.py:140-185` runs the FORMAT check
(`AgentValidator:format`, `"constraint_type": "hard"`,
`"expected_terminal": True`) ahead of any semantic rule validator. Its own
comment (`agent_validator.py:175-181`) states this explicitly: "DELIBERATELY
no 'rule_id' (2026-06-10): this result fires on EVERY row of the frozen mock
baselines (mock output lacks the PMT appraisal fields), so the audit CSV's
failed_rules column shows 'Unknown' for it BY FREEZE -- adding a rule_id
here flips every frozen-baseline row and breaks mock byte-identity
re-verification." Because mock's response can never satisfy this format
gate, it never reaches a semantic RULE validator (e.g. `extreme_threat_block`),
so mock is structurally incapable of producing a rule-level intervention --
no run-time flag changes that, because the gap is in what `mock_invoke`
returns, not in agent state or prompt wording.

This is directly confirmed by the four runs already produced for this
recipe. `governance_summary.json` for all four runs reports
`"total_interventions": 0` and `"rule_frequency": {}` (zero rule-level
interventions, matching the code-level reasoning above), but ALSO reports
`"outcome_stats": {"parse_errors": 1000}` and `"llm_level_retries":
{"invalid_label_retries": 1000, "total_extra_llm_calls": 1000}`. The raw
per-agent trace (`raw/household_traces.jsonl`) confirms this at the row
level: every one of the 500 rows in every run has `retry_count: 3`,
`format_retries: 2`, `validated: false`, `decision_source:
"validator_rejected"`. So the premise that "0 interventions" means the
retry loop was never exercised is not accurate as stated:
`_governance_retry_loop` (the function PR #46 changes) fired 1000 times per
run, via the FORMAT-violation branch, which is the exact branch
`test_format_violation_path_under_placebo_mode_...` and
`test_format_violation_path_under_full_mode_...` exercise. What "0
interventions" correctly describes is that the RULE-violation branch (the
one carrying a real `rule_id`, e.g. `extreme_threat_block`) never fired,
because mock can never pass the format gate to reach it.

Checked `--stress-test {veteran,panic,goldfish,format}` (a flag on
`run_flood.py`, lines 967-1001) as a candidate "one-flag switch": all four
stress profiles only rewrite `narrative_persona` (prompt TEXT), which
`mock_invoke` ignores entirely -- it extracts the first numbered option by
regex and never reads persona content. No stress-test flag, and no other
flag on `run_flood.py`, changes what `mock_invoke` returns. No
`FakeTraffic`-style rule-violating mock fixture is wired to `run_flood.py`:
`examples/_test_fixtures/fake_traffic/` is a DomainPack genericity-test
fixture consumed by `broker/tests/test_genericity_runtime_gate.py` and
`tests/integration/test_e2e_genericity.py`, not reachable through
`run_flood.py --model mock`. No one-flag switch exists that would make mock
exercise a rule-level intervention, so no new run was made for this step.

`SUBMISSION_2026/reviewer_prep_2026-09-05/out/regen_progress_2026-09-15.md`
documents a DIFFERENT prior mock byte-identity gate, c3391a53 vs faf1bb12
(a separate commit pair, the cross-model gemma4:12b wiring), also
"IDENTICAL after ignoring the five additive telemetry columns" -- the same

closest existing empirical evidence in this repo that the full-vs-placebo

### 3. Honest conclusion

The mock byte-identity check proves the whole flood single-agent pipeline
outside the retry-prompt text itself (agent setup, memory, environment,
format-violation retry counts, validator dispositions, final skill
execution, and every audit and simulation-log artifact) is unchanged
between c3391a53 and 83fa97e1, with the sole observed diff being the new
`retry_feedback_mode` manifest field; the retry loop that PR #46 edits is
covered only by the unit tests named above, which pin the default
resolution to "full" and pin full-mode's textual content by fixed literal
assertion plus by direct code inspection of `_governance_retry_loop` and
the format-check comment in `agent_validator.py`, none of which is an
automated diff against actual c3391a53 output. What remains unproven by
anything run so far is whether the retry-prompt TEXT rendered under full
mode at 83fa97e1 is byte-identical to what the pre-PR code rendered, since
the mock model's own response generator is blind to prompt content and so
could never have surfaced a textual regression in that prompt even if one
existed.

## Retry-prompt golden text

Follow-up closing the gap left by "Retry-path evidence" above: that section
established, by code inspection and unit-test citation, that no automated
test diffs the full-mode retry-prompt TEXT against real c3391a53 output.
This section closes that gap empirically: it renders the actual retry
prompt through the real code (`_governance_retry_loop`, `_advise.py`,
`UnifiedAdapter`) at each commit, using a fixed deterministic fixture, and
diffs the rendered text directly.

Source reading first, since it explains why the result below is unsurprising:
`diff broker/core/_advise.py` and `diff broker/utils/parsing/unified_adapter.py`
between the two worktrees are byte-identical (empty diff, exit code 0) --
neither file changed in PR #46 at all. `diff broker/core/_retry_loop.py`
shows the only change is that the single unconditional call
`render_intervention_prompt(self.model_adapter, prompt, errors_to_send,
max_reports=self.max_reports, framing=getattr(self, "_intervention_framing",
"legacy"))` at c3391a53 became the `else:` (full-mode) branch of a new
if/elif/else at 83fa97e1, reached via `getattr(self, "_retry_feedback_mode",
"full")` defaulting to "full", with IDENTICAL arguments to the c3391a53
call. The `errors_to_send` construction above it (the rule-violation vs
format-violation branching) is unchanged text, line for line, between the
two commits. So the golden-text check below is confirming, empirically,
what static code reading already predicts.

### Script (verbatim)

Written to the scratchpad as `render_full_prompt.py`, run from the primary
repo against each worktree root as `argv[1]`:

```python
"""Golden-text comparison script for the c3391a53 vs 83fa97e1 mock-equivalence
recipe (see .baselines/MOCK_EQUIV_c3391a53_83fa97e1_flood.md, "Retry-prompt
golden text" section).

Renders the retry prompt EXACTLY the way `_governance_retry_loop`'s
default/full-mode branch does, by calling the real method on a minimal
RetryMixin host, the same way `broker/tests/test_retry_feedback_placebo.py`
does (`_Host._governance_retry_loop(llm_invoke=..., **kwargs)`, capturing the
`retry_prompt` argument the mixin passes to `llm_invoke`). Two fixed,
deterministic scenarios are covered:

  1. A rule-violation retry: a real SkillProposal plus three deterministic
     ValidationResult objects, each carrying a rule_id (metadata["rules_hit"]),
     a reason (errors[0]) and a suggestion (metadata["suggestion"]).
  2. A format-violation retry: skill_proposal=None, which makes
     `_governance_retry_loop` build its own hardcoded synthetic
     "format_violation" InterventionReport (see broker/core/_retry_loop.py,
     the `if not skill_proposal:` branch), independent of validation_results.

At c3391a53, `_governance_retry_loop` has only ONE rendering path (no
`_retry_feedback_mode` concept exists in that commit's code at all): it always
calls `render_intervention_prompt(self.model_adapter, prompt, errors_to_send,
max_reports=self.max_reports, framing=getattr(self, "_intervention_framing",
"legacy"))`. At 83fa97e1 the same call is the `else:` (full-mode) branch of a
new if/elif/else on `getattr(self, "_retry_feedback_mode", "full")`, reached
whenever that attribute is absent or equals "full" -- with IDENTICAL
arguments to the c3391a53 call. This script's `_Host` deliberately never sets
`self._retry_feedback_mode`, so at 83fa97e1 it takes the `else:` (full) branch
via the getattr default, and at c3391a53 the attribute is simply never read.
Same fixture, same code path semantics, at both commits.

Usage: python render_full_prompt.py <worktree_root>
"""
import sys

if len(sys.argv) != 2:
    print("usage: python render_full_prompt.py <worktree_root>", file=sys.stderr)
    sys.exit(2)

WORKTREE_ROOT = sys.argv[1]
sys.path.insert(0, WORKTREE_ROOT)

from broker.core._retry_loop import RetryMixin  # noqa: E402
from broker.interfaces.skill_types import SkillProposal, ValidationResult  # noqa: E402
from broker.utils.parsing.unified_adapter import UnifiedAdapter  # noqa: E402


class _NoopAuditor:
    def log_parse_error(self):
        pass


def _real_adapter():
    # UnifiedAdapter.format_intervention_prompt / format_retry_prompt reference
    # no self.* state (confirmed by reading the method body, and by
    # test_retry_feedback_placebo.py's own `_real_adapter` helper docstring),
    # so `__new__` without `__init__` is safe and matches how the test suite
    # builds the adapter for exactly this kind of prompt-rendering check.
    return UnifiedAdapter.__new__(UnifiedAdapter)


class _Host(RetryMixin):
    max_retries = 1
    max_reports = 3

    def __init__(self):
        self.auditor = _NoopAuditor()
        self.model_adapter = _real_adapter()
        # Deliberately NOT setting self._retry_feedback_mode -- see module
        # docstring above for why this is the correct way to compare "full"
        # mode at 83fa97e1 against the only behaviour at c3391a53.

    def _run_validators(self, proposal, context):
        # Only consulted after the single retry attempt below; max_retries=1
        # means the loop exits after that attempt regardless of this return
        # value, so its content does not affect the rendered retry prompt.
        return [ValidationResult(valid=True, validator_name="ok")]


ORIGINAL_PROMPT = (
    "ORIGINAL PROMPT TEXT -- fixed golden-text fixture for the "
    "c3391a53 vs 83fa97e1 retry-prompt comparison."
)

RULE_ID_1 = "low_coping_block_v9"
REASON_1 = "insufficient adaptive coping capacity for elevate_structure"
SUGGESTION_1 = "Consider a lower-cost adaptation such as buy_insurance instead."

RULE_ID_2 = "affordability_cap_v3"
REASON_2 = "proposed magnitude exceeds the agent's affordability ceiling"
SUGGESTION_2 = "Reduce the magnitude_pct to within the agent's affordability cap."

RULE_ID_3 = "extreme_threat_block"
REASON_3 = "extreme threat appraisal combined with a do-nothing skill is blocked"
SUGGESTION_3 = "Given VH threat appraisal, choose relocate or buy_insurance instead of do_nothing."


def _rule_violation_results():
    """Three deterministic validation errors, each with rule_id, reason and
    suggestion -- the shape `build_intervention_reports` (broker/core/
    _advise.py, source="errors") reads: rule_id from
    metadata["rules_hit"][0], reason from errors[0], suggestion from
    metadata["suggestion"]."""
    return [
        ValidationResult(
            valid=False, validator_name="AgentValidator:thinking_error",
            errors=[REASON_1],
            metadata={"rules_hit": [RULE_ID_1], "suggestion": SUGGESTION_1,
                      "deterministic": True},
        ),
        ValidationResult(
            valid=False, validator_name="AgentValidator:governance_rule",
            errors=[REASON_2],
            metadata={"rules_hit": [RULE_ID_2], "suggestion": SUGGESTION_2,
                      "deterministic": True},
        ),
        ValidationResult(
            valid=False, validator_name="AgentValidator:governance_rule",
            errors=[REASON_3],
            metadata={"rules_hit": [RULE_ID_3], "suggestion": SUGGESTION_3,
                      "deterministic": True},
        ),
    ]


def _common_kwargs(*, skill_proposal, validation_results):
    return dict(
        all_valid=False,
        skill_proposal=skill_proposal,
        validation_results=validation_results,
        all_validation_history=list(validation_results),
        validation_context={},
        prompt=ORIGINAL_PROMPT,
        context={},
        agent_id="H01",
        agent_type="household",
        env_context={"current_year": 1},
        raw_output="raw",

def _capture_retry_prompt(**kwargs):
    captured = {}

    def llm_invoke(retry_prompt):
        captured["prompt"] = retry_prompt
        return SkillProposal(
            skill_name="do_nothing", agent_id="H01", agent_type="household",
            reasoning={},
        )

    host = _Host()
    host._governance_retry_loop(llm_invoke=llm_invoke, **kwargs)
    return captured["prompt"]


def main():
    # Branch 1: rule-violation retry.
    rule_prompt = _capture_retry_prompt(**_common_kwargs(
        skill_proposal=SkillProposal(
            skill_name="elevate_structure", agent_id="H01",
            agent_type="household", reasoning={},
        ),
        validation_results=_rule_violation_results(),
    ))

    # Branch 2: format-violation retry (skill_proposal=None).
    format_prompt = _capture_retry_prompt(**_common_kwargs(
        skill_proposal=None,
        validation_results=_rule_violation_results(),
    ))

    print("=== RULE-VIOLATION RETRY PROMPT ===")
    print(rule_prompt)
    print("=== END RULE-VIOLATION RETRY PROMPT ===")
    print()
    print("=== FORMAT-VIOLATION RETRY PROMPT ===")
    print(format_prompt)
    print("=== END FORMAT-VIOLATION RETRY PROMPT ===")


if __name__ == "__main__":
    main()
```
