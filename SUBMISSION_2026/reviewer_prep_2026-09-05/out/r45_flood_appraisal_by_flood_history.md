# R45 -- Flood first-stated threat appraisal by household flood history

Generated by `SUBMISSION_2026/reviewer_prep_2026-09-05/scripts/r45_flood_appraisal_by_flood_history.py`. CPU-only, existing runs only, no LLM calls. Pre-registered report-only item (spec item 33f, decided 2026-10-01): the flood analogue of the irrigation R5 table -- does a household's FIRST-STATED threat appraisal fade with time since its last flood? Descriptive only; no claims beyond the numbers shown.

## Method

**Flood-experience field**: `simulation_log.csv` column `memory`, parsed for the exact per-year sentence `examples/single_agent/run_flood.py (FinalParityHook.pre_year)` appends every year, BEFORE that year's governance decision runs. 'Experienced a flood' = the household's OWN house took damage that year ("Got flooded with $10,000 damage on my house." / "Despite elevation, the flood was severe enough to cause damage."), not merely a regional flood event with no personal loss ("A flood occurred, but my house was spared damage." / "...protected by its elevation.") and not no flood at all ("No flood occurred this year."). The lookup scans every `simulation_log.csv` row regardless of that row's own `relocated` flag: a sample household whose OWN decision that year was to relocate still has a real "Year Y: ..." sentence on that row (checked on-disk), because `relocated` reflects the state AFTER the decision while the sentence is written BEFORE it; years strictly after relocation correctly resolve to 'not found' because no new sentence is ever written then. Both history measures below are computed INCLUSIVE of the current decision year, because the household's own current-year outcome is already recorded before that year's decision (see the script's own module docstring for the verification). `broker/domains/water/providers.py (FinancialCostProvider)`'s `years_since_flood` field was checked and is wired only into the multi-agent flood domain, not into `examples/single_agent/run_flood.py` -- not used here. `flood_count` DOES appear in `examples/single_agent/run_flood.py`, but only as a reflection trait (`FinalParityHook.post_year`, `ctx.custom_traits["flood_count"]`, fed to the batch reflection prompt, not to the household's own decision prompt) -- a different field for a different purpose, not used here either.

**First-stated threat appraisal**: calls `r44_flood_ibr_first_attempt.py (first_attempt_proxy)` directly for every row (imported, not restated -- B1 fix, 2026-10 review round: an earlier version of this script re-derived the same retry_count/failed_rules branch logic instead of calling r44's own function, which could have silently drifted from it). r44's own resolver only ever returns a HIGH/LOW/'not resolved' bin, never the exact VL..VH label, so for the one branch where this script also needs the exact label (`retry_count == 0`, the first attempt is also the final attempt) it separately reads `construct_TP_LABEL` and ASSERTS the bin derived from that label agrees with r44's own bin for the identical row -- the two readings of one branch can never silently disagree. For a retried row, r44's resolver can only recover a HIGH/LOW bin (via which rule blocked the first attempt), never the exact label -- a real limit of what the governance validators recorded, not a choice made here, and this script does not attempt to re-derive anything finer than what r44 itself returns for that branch. The primary tables below therefore use exact-label rows only; retried rows are counted and reported as a labelled coarse-bin sensitivity line beside each table, never silently dropped and never guessed into a specific label.

**Format-retries note** (item 5, 2026-10 round-3 review): `retry_count` counts GOVERNANCE retries only; `format_retries` (a separate audit column) counts parse-level retries before the output even reached a governance check. 431 of 28737 (1.50 percent) exact-label (`retry_count == 0`) rows, pooled across all six arms, had `format_retries > 0` -- computed live, not assumed. 'First-stated' therefore means the first attempt that PARSED (the same sense in which r44's own `initial_labels` column, on the strict_initprop arm, is understood to hold the first attempt), not necessarily the model's very first raw generation if an earlier one was malformed and silently re-prompted for format alone.

**Corpus and arms**: identical to r44 -- `defaults` (primary, commit 83fa97e1) strict_n10/disabled_n10 (seeds 42-51) and placebo (seeds 42-43); `v08` (appendix, commit mix: strict/disabled at faf1bb12, placebo at 83fa97e1) at seeds 42-46/42-43. Single model (gemma3:4b) -- r44's own arm scope never includes another model, so there is no per-model split to report. Directory names and seed lists come from `_common.py (flood_corpus_dirs)`, via `r44_flood_ibr_first_attempt.py`'s own `ARMS` list, never a local literal.

**Buckets**: years since last flood -- this year (0), 1, 2, 3, 4+, never flooded (no flood recorded in 1..current year). Floods so far -- 0, 1, 2, 3+ (inclusive of the current year).

**Memory visibility** (item 1, 2026-10 review round): these runs use a 5-item sliding-window memory (`examples/single_agent/run_flood.py (run_parity_benchmark)` defaults `memory_engine_type="window"`, `window_size=5`; the per-decision memory actually exported is retrieved by `FinalParityHook.post_year`'s `retrieve_content_only(agent, top_k=5)` / `retrieve(agent, top_k=5)` call), confirmed live by measuring every record's `memory_pre` list length (capped at 5; one individual seed-run from each of the six arms shows the SAME per-seed-run length distribution -- a simulation-wide constant, not a governance effect -- this identity holds PER SEED-RUN, not pooled across an arm's several landed seeds). The Memory visibility section below checks, for each years-since-last-flood bucket, what share of decisions still have their own last-damage sentence inside that window at decision time, read from `memory_pre` in `raw/household_traces.jsonl` (present for every seed in all six arms -- confirmed by direct file-existence check, not assumed). A drop in mean TP while the sentence is STILL visible in the prompt is NOT caused by the sentence leaving the window (it has not left); protection state is also changing across these same years (see Protection confound below), so that drop is not attributed to 'the model's own weighting' alone either -- only the leaving-the-window explanation is ruled out for it. A further drop AFTER the sentence has left the window is at least partly attributable to the memory design itself.

**Exclusions counted beside every mean**: ABORTED status (checked live on this corpus; see each arm's totals below for the actual count) and blank or off-vocabulary first-stated label, plus two further categories specific to this method: bin-only (retried, exact label unrecoverable) and unresolved (retried, first-blocking rule not R1/R3/R4). A row is placed in a flood-history bucket independently of whether its TP label is known, so the exclusion counts shown per bucket reveal whether exclusion concentrates in particular history buckets rather than spreading evenly.

**Protection confound check** (item 2, 2026-10 review round): protection state -- elevated / insured only / both / neither -- is read AT DECISION TIME from the trace's own `state_before` field (`raw/household_traces.jsonl`), never `state_after` and never `simulation_log.csv`'s `elevated`/`has_insurance` columns. Checked and confirmed live (sample household, defaults/strict_n10 arm, seed 42): `state_before.elevated` is False at year 1, the SAME year that household's decision elevates it, and `state_after.elevated` is True that same year, matching `simulation_log.csv`'s own `elevated` column for that row exactly -- proving `simulation_log.csv`'s protection columns are POST-decision, so they are never used for this split. `state_before` is present and complete (both keys present) on every decision record checked, with `state_before.relocated` never True (a relocated household never makes another decision, so it never reaches this script's rows at all).

## Limitations

1. The primary (exact-label) table is a SELECTION on rows whose first attempt was never retried. Retried rows are disproportionately the HIGH-threat/do_nothing and LOW-threat/relocate-or-elevate cases -- exactly the extremes most relevant to a fading-salience question -- so the primary table under-represents exactly the rows this question cares most about on arms where governance is active (strict, placebo). The disabled arm never retries at all, so its exact-label table has no such selection. BIAS DIRECTION (B2 fix, 2026-10 round-3 review): A HIGH-bin row can only raise a bucket's exact-label mean and a LOW-bin row only lower it; in buckets 1 through 4+ and never flooded, 1286 of 1372 (93.7 percent) excluded bin-only rows are HIGH-bin (R1), 86 are LOW-bin (R3/R4), so the exact mean in those buckets is biased DOWN relative to what the full sample would show; in 'this year', 108 HIGH-bin (R1) vs 27 LOW-bin (R3/R4) of 135 excluded bin-only rows, so the LOW rows there leave the net bias direction open rather than pointing one way. Putting the excluded bin-only rows of each bucket back at the low and high end of their own bin (the full range consistent with their unknown exact label -- never a guess at the true value) gives, per governed arm: defaults/strict: this year [3.70, 3.79] (n=633 exact + 69 bin) vs 4+ [3.09, 3.13] (n=1147 exact + 50 bin) and never flooded [3.16, 3.22] (n=5172 exact + 341 bin) -- ranges do not overlap; defaults/placebo: this year [3.79, 3.90] (n=136 exact + 18 bin) vs 4+ [2.89, 2.93] (n=270 exact + 10 bin) and never flooded [3.10, 3.16] (n=1020 exact + 71 bin) -- ranges do not overlap; v08/strict: this year [3.79, 3.87] (n=319 exact + 30 bin) vs 4+ [3.08, 3.12] (n=620 exact + 29 bin) and never flooded [3.15, 3.21] (n=2476 exact + 154 bin) -- ranges do not overlap; v08/placebo: this year [3.69, 3.81] (n=127 exact + 18 bin) vs 4+ [3.12, 3.16] (n=240 exact + 10 bin) and never flooded [3.14, 3.23] (n=1009 exact + 92 bin) -- ranges do not overlap.
2. 'Experienced a flood' is defined at the household level (own-house damage), not at the community level (a flood event occurring that year regardless of personal damage). A household can correctly report 'not flooded' in a year when a regional flood event occurred, if its own house was spared or protected by elevation.
3. Years since last flood and floods-so-far are both computed INCLUSIVE of the current decision year (see Method) -- a household flooded this year has years-since = 0, not 'undefined' or '1'.
4. A flood-history coverage gap (a year in 1..current year with no resolvable own-year sentence anywhere in that agent's `simulation_log.csv` rows) excludes the row from every bucket table; the per-arm counts above report how often this happened on this corpus -- it was not assumed to be zero (live total across all six arms: 0 of 30250 rows).
5. No statistical test, trend line, or causal claim is computed anywhere in this report. The 'Plain reading' paragraph above states the full 6-bucket mean sequence actually observed, by arm, with each bucket's own n -- '4+' and 'never flooded' are always reported separately, never merged into one tail number.
6. Scope matches r44 exactly: only strict, disabled, and placebo, in the defaults and v08 corpora. Paraphrase/no-nudge/gemma4:12b/rule-based arms are out of scope here for the same reasons r44 excludes them (see r44's own Limitations item 6).
7. Audit-trail gap (item 6, 2026-10 review round): some active agent-years per arm have a `simulation_log.csv` row (a real decision should exist) but no `household_governance_audit.csv` row and no trace record at all, so they never reach the ABORTED count or any other count in this report -- the same gap r44 itself cannot see, since r44 also only ever reads rows that exist in the audit CSV. Per-arm counts are printed in each arm's own 'Audit-trail gap' line above (computed live from this corpus, not assumed to be zero and not copied from any prior estimate).
8. Memory visibility (item 1, 2026-10 review round): a mean-TP drop that occurs WHILE the household's last-damage sentence is still inside its 5-item memory window reflects the model's own weighting of that information -- the sentence was there to read and the stated appraisal still fell. A further drop AFTER the sentence has rolled out of the window cannot be attributed to the model alone in the same way: at that point the information literally is not in the prompt, so part (not necessarily all) of that later drop may be the memory design rather than the model discounting a flood it can still see. The Memory visibility section above reports the visible-vs-not-visible split needed to tell these two apart within a bucket, instead of only the window-size fact.
9. Protection confound (item 2, 2026-10 review round): the top-line tables above do not hold protection state constant, so any decline they show could be entirely a PMT-consistent, rational lowering of threat by households that elevated, insured, or both -- not fading memory at all. The Protection confound section reports the decline SEPARATELY within the unprotected ('neither') group and the protected group; only a decline that also appears within 'neither' (where no protection-driven reason to lower threat exists) is evidence against a pure-PMT explanation. Cells below n=20 are shown as 'n too small' rather than a mean. The PER-ARM table is the 2-way split (neither vs protected) only -- its sparse cells are overwhelmingly 'neither': always thin in buckets '1' through '4+' (n<=4 per arm on every arm checked), and also thin at 'this year' specifically on the two 2-seed placebo arms (n=13, n=15); 'protected' is not thin in any arm or bucket checked (always in the hundreds or more). The POOLED table is the 4-way split; there, 'neither' past 'this year' and 'insured only' past '1' are the cells most likely to be thin -- see the n<20 flags printed directly in that table, never omitted.
